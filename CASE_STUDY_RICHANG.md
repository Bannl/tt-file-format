# Case study: the voice files of Rìcháng

[Rìcháng](https://github.com/Bannl/Richang) is a game to learn the 2,000 most common words of Taiwan Mandarin. Its
4,728 voice lines are stored as TT files: one Ogg Opus file per character, and two for the player. They were the
first Ogg TT files written outside AudioCrucible and the test kit, and the data set on which the weight rules of
draft 0.3 were measured: the segment table (section 11.5 of the [specification](SPEC.md)), deflated original chunks
(section 5.2), silence between sounds (section 11.4) and the reference weight (section 12). This document gives the
method and the results. Units: 1 MB = 10^6 bytes, 1 KB = 10^3 bytes.

## 1. Summary

- **Ogg Opus, files as shipped.** With draft 0.3 (segment table, no silence added between lines), the 36 files of
  the game weigh 32,880,191 bytes, 5.24 % less than their reference weight, the size of the same lines as separate
  files with the same metadata (section 12.1). Every file is lighter, by 4.07 % to 7.51 %. Written as for draft 0.2
  (XML list, 300 ms of silence between lines), the same voices were 17.5 % heavier than their reference weight.
- **Ogg Opus and Ogg Vorbis, against re-encoded files.** Against the 4,725 lines encoded one by one as separate files
  with the same tags, the TT files went from 16.4 % heavier to 7.4 % lighter in Ogg Opus, and from 21.2 % to 32.1 %
  lighter in Ogg Vorbis.
- **WAV.** A WAV TT file and its separate files weigh about the same (0.09 % less for the TT file), and 2.2 ms of
  silence per sound outweighs the difference. When the original chunks of each sound are kept
  (`ORIGIN/CHUNK_LIST`), deflating them turns an estimated 0.26 % excess into 0.69 % less, on 475 sound effects.
- **Nothing is lost.** Converted from the XML list to the table and back, every element and every value of every
  line came back, in the same order: 4,725 segments of the 36 Opus files of draft 0.2, and 9,450 segments of the 72
  rewritten files.

## 2. The data

### 2.1 Lines and audio

- 34 characters, one per situation of the game (convenience store, night market, landlord, clinic, immigration
  office...), and the player, who has a female and a male voice. Each character file holds the lines of that
  character; each player file holds all the lines of the player in one voice. 4,728 lines in all: 1,576 for the
  characters, 1,576 for each voice of the player (with the 3 lines of the tutorial).
- The lines are generated by speech synthesis (CosyVoice 3, `Fun-CosyVoice3-0.5B`), each voice prompted by a
  recording of a Taiwanese speaker from Mozilla Common Voice zh-TW 27.0. The source WAV files are 24 kHz, 16-bit,
  mono. Each line is trimmed at −45 dBFS and keeps 50 ms of quiet before the speech and about 120 ms after it.
- The study corpus (2026-11-12, before the tutorial): 4,725 lines, 10,098 s of speech, 2.14 s per line on average;
  33 to 1,575 lines per file (median 45).

### 2.2 TT files

- **Writer**: the build script of the game (Node.js, a port of the kit's Ogg functions). ffmpeg 6.0 encodes the
  audio: libopus at 20 kbit/s (`-application voip`, mono), and, for the comparison, libvorbis at quality 0, 24 kHz,
  mono. The script then writes the comment header again; the audio packets are kept byte for byte.
- **One segment per line**: `NAME` is the key of the line (for example `tutorial-0-n`); `SEGMENT_ID` is the
  name-based UUID (version 5) of that key, the same from one build to the next (section 5.1). `USER` holds the UCS
  fields (`VOXFem` or `VOXMale`, FXName, description, keywords, creator, source, library). `FIELD_LIST` holds ten
  fields: situation, scene, line number, speaker, voice, topic, the text of the line in Chinese, its pinyin, English
  and French. `ORIGIN` names the source WAV file and its range, at 24 kHz.
- **File level**: a chapter per line up to the 999th; the 577 later lines of each player file are in the list only
  (section 11.2). The summary (`TITLE`, `DESCRIPTION`, `COMMENT`, `KEYWORDS`) and `AUDIO_SHA256`.
- **Reader**: the game (TypeScript, Web Audio) reads the list in the file, XML or table, and decodes only the
  packets that cover a line (section 11.4): about 10 to 14 ms per line. Parsing the table of a player file (1,575
  lines) took about 2 ms in Node.js.

### 2.3 The forms compared

| Form | Segment list | Silence between lines | Draft |
|---|---|---|---|
| As written for draft 0.2 | XML, `TT_SEGMENT_LIST` | 300 ms (100 ms before the first line, 300 ms after the last) | 0.2 |
| No silence | XML | none: each line keeps its own quiet edges | 0.2 |
| Table | `TT_SEGMENT_TABLE`, with `ORDER` | none | 0.3 |

## 3. Method

### 3.1 Separate files

Each line was encoded alone from its range of the source WAV file, with the settings of the writer: 4,725 lines and
2 codecs, 9,450 encodings. Its metadata, the 30 values of its segment (`USER` 10, `FIELD_LIST` 10, `ORIGIN` 9,
`NAME` 1), was counted as the Vorbis comments of a separate file (4 bytes of length, the name, `=`, the value):
1,018 bytes per line on average.

| Separate files | Ogg Opus | Ogg Vorbis |
|---|---|---|
| Without tags | 26,083,133 bytes | 50,540,106 bytes |
| With the same metadata as tags | 30,892,868 bytes | 55,264,791 bytes |

### 3.2 Reference weight

The reference weight (section 12.1) is computed from the TT file itself: its header pages with a comment header
reduced to the vendor string, the values of each segment as tags, the audio packets that hold the frames of each
segment (a packet shared with another segment counts in proportion), their lacing values and their pages. It does
not depend on an encoder run, and the kit's `--validate` prints it. On the study files it was 1.3 % below the
re-encoded separate files (30.49 MB against 30.89 MB in Ogg Opus, 54.55 MB against 55.26 MB in Ogg Vorbis): it is
the stricter of the two baselines.

### 3.3 WAV

- **Model**: the same lines as one WAV TT file per character (24 kHz, 16-bit, mono, full marker mirror, `LIST/INFO`,
  `ORIGIN`), against separate WAV files that each carry `fmt `, `bext` and an iXML chunk with the `USER` and
  `FIELD_LIST` blocks of the line. One character (75 lines) was also written as a WAV TT file and as 75 separate WAV
  files.
- **Original chunks**: on 475 WAV sound effects of a test library (600 MB), the cost of `ORIGIN/CHUNK_LIST` (the
  chunks AudioCrucible keeps: `bext`, `LIST-INFO`, `iXML`, `_PMX`, `id3`) was computed in four forms, from the
  chunks of each file and the cost of a segment in a WAV TT file. These figures are estimates: no TT file was written
  for these sounds.

### 3.4 Tools

Python 3.11, ffmpeg 6.0 with libopus and libvorbis, and the kit of this repository. The scripts of the study are not
published here; the reference-weight figures can be checked on the files of Rìcháng (section 14).

Per line, TT file minus separate files with tags, average over the 36 files:

| Lacing values | +14.2 | −0.8 |

- A separate Ogg Opus file spends little on its own headers: 103 bytes for an empty stream, 125 bytes per file in
  median as measured (41 to 230). That is all a TT file can save per line in Ogg Opus.
- The XML list costs 743 bytes per line more than the tags of a separate file: the markup of each `FIELD` (43 bytes,
  against 5 for a tag), the names of the `USER` elements, and the structure of the segment (`TT_SEGMENT`,
  `SEGMENT_ID`, `CUE_ID`, positions: 181 bytes). No uncompressed XML form can fall below the headers saved: reduced
  to its ID, name and position, the XML of a segment still takes 215 bytes.
- The table writes each value with 3 bytes of syntax (two quotes and a comma) and each column name once: per field it
  costs the length of the name plus 2 bytes less than a tag. Values that every line of a file shares are written
  once, in `DEFAULTS`. 1,761 bytes per line as XML, 540 as a table, against 1,018 for the tags.
- The 300 ms of silence between lines cost 342 bytes per line in median (311 to 401 by file). On one player file,
  20, 40 and 100 ms cost 37, 71 and 152 bytes per line.

- In WAV the audio is the same bytes on both sides, and the metadata balance within 100 to 450 bytes per sound. The
  margin equals 2.24 ms of silence per sound at 24 kHz, 16-bit, mono, and 0.38 ms at 48 kHz, 24-bit, stereo: a WAV
  TT file is lighter than its separate files only when all its audio belongs to its segments.
- The balance depends on the `bext` chunk of the separate files (638 bytes each). Without it, a separate file pays
  140 bytes on its own, less than the list entry of a segment.
- One character (75 lines) written both ways: 7,422,300 bytes for the TT file, 7,428,620 bytes for the 75 separate
  files (−0.09 %). The TT file passes `--validate`, and its reference weight equals, to the byte, the size of the 75
  files written.

### 6.2 Original chunks (estimate)

475 WAV sound effects of mixed origins, 600 MB, 11,440 bytes outside the audio per file on average (118 bytes in
median). The chunks AudioCrucible keeps take 10,470 bytes per file on average (in 248 files of 475), mostly XMP
packets (`_PMX`, 26 KB on average in 167 files).

| Form of `ORIGIN/CHUNK_LIST` | TT file minus original files | Per sound, median | Sounds heavier in the TT file |
|---|---|---|---|
| Not kept (a split no longer restores the chunks) | −0.85 % | +577 bytes | 278 of 475 |
| Base64 (draft 0.2) | +0.26 % | +660 bytes | 466 of 475 |
| Deflated, then base64 (draft 0.3) | −0.69 % | +621 bytes | 294 of 475 |
| Binary, in a RIFF chunk of their own (not in the draft) | −0.02 % | +633 bytes | 458 of 475 |

Deflated then base64, relative to the original bytes: `_PMX` 0.15, `bext` 0.18, `iXML` 0.25, `ID3 ` 0.64, `id3 `
1.05, `LIST-INFO` 1.26 (too small to gain). The median stays positive: most of these files hold almost nothing
outside their audio, and the TT file writes for each sound its IDs, name, origin and markers, about 600 bytes, that
is 0.05 % of an average sound of this set (1.25 MB).

### 6.3 FLAC (open question 3)

The 75-line WAV TT file as one FLAC file: 2,983,317 bytes. The 75 separate WAV files as 75 FLAC files: 3,598,285
bytes, of which 8,286 bytes of headers and padding each (`PADDING` 8,192 bytes as written by ffmpeg). The TT file is

## 8. Silence between lines

Measured on 400 lines of one player file, decoded with 300 ms of silence between lines and with none:

- **Lines as they are** (50 ms of quiet before the speech, about 120 ms after it): the signal-to-noise ratio of each
  line against its source does not change (Ogg Opus 11.68 dB; Ogg Vorbis 16.93 dB and 16.92 dB). Over the first and
  the last 20 ms of a line, the two decodes differ by −72 to −89 dBFS in median, −41.5 dBFS at worst; over the middle
  half of a line, they already differ by −33 to −36 dBFS in median.
- **A loud end followed by a quiet start** (395 junctions): rise of the first 20 ms of the quiet line, against the
  same line after 300 ms of silence:

| Silence | Ogg Opus | Ogg Vorbis |
|---|---|---|
| 0 ms | +33.0 dB in median; 395 of 395 above +6 dB | +29.7 dB; 395 of 395 above +6 dB |
| 20 ms | +4.6 dB; 156 above +6 dB | +10.2 dB; 252 above +6 dB |
| 40 ms | 0.0 dB; worst +11.7 dB; 4 above +6 dB | 0.0 dB; worst +3.6 dB; none above +6 dB |
| 60 ms | 0.0 dB; worst +1.9 dB; none above +6 dB | 0.0 dB; worst +4.9 dB; none above +6 dB |

- **Two loud edges joined** (395 pieces): over the 10 ms of the edge, Ogg Vorbis loses 4 dB of signal-to-noise ratio
  (17.05 dB, against 21.22 dB for the piece encoded alone and 16.9 dB in the body of the sounds), Ogg Opus 0.2 dB.
  20 ms of silence give back most of it in Ogg Vorbis (20.21 dB).

These results gave the note of section 11.4: no silence between sounds whose edges are quiet; 40 ms (Vorbis) to
60 ms (Opus) after a loud end; a little silence at each end of the file.

## 9. Number and length of the sounds

The first N lines of one character file, written as a TT file with no silence (Ogg) or as a WAV TT file:

| Format | The TT file is the lighter one from |
|---|---|
| Ogg Vorbis, table | 2 segments |
| Ogg Opus, table, against the reference weight | 5 segments (4 against the re-encoded files with tags) |
| WAV, full marker mirror and `ORIGIN` | 13 to 14 sounds |
| WAV, without `note`, `LIST/INFO` and `ORIGIN` | 3 to 4 sounds |

A file of one segment is always heavier (by 0.4 to 1.6 KB): it pays a list header and a marker mirror, and shares
nothing.

What a TT file saves is fixed per sound, so its share falls as the sounds grow longer. Computed from the measured
terms of sections 4.2 and 5 (only the 2.14 s row is measured):

| Length of a sound | Ogg Vorbis, quality 0, table | Ogg Opus, 20 kbit/s, table |
|---|---|---|
| 1 s | about −48 % | about −13 % |
| 2.14 s (measured) | −32.1 % | −7.5 % |
| 10 s | about −10 % | about −2 % |
| 60 s | about −1.8 % | about −0.3 % |

Against re-encoded separate files, the comparison also carries the variation of the encoder: encoded end to end, the
audio packets of a file differed from the same lines encoded alone by −1.87 % to +1.94 % in Ogg Opus (median
+0.40 %), and by −1.20 % to −0.09 % in Ogg Vorbis (median −0.72 %). Beyond about 25 KB of audio per sound, this
variation exceeds what the TT file saves; the reference weight, computed from the packets of the file itself, does
not vary.

## 10. Approaches measured and not retained

| Approach | Measured | Why it is not in the draft |
|---|---|---|
| XML list deflated, in base64 | Ogg Opus −11.79 % (table: −7.44 %) | the list can no longer be read as text; open question 5 |
| One comment per segment | +19 bytes per segment | ffmpeg 6.0 joins comments of the same name with `;`, and RFC 7845 lets an Ogg Opus program drop the comments beyond 61,440 octets, which would cut such a list without notice |
| Binary data after the comments of `OpusTags` | saves the base64 of a deflated list | ffmpeg 6.0 drops it when it rewrites a file; no equivalent in Ogg Vorbis |
| Opus DTX (libopus) | at most about 90 of the 342 bytes of 300 ms | it starts after 200 ms of silence: nothing on 60 ms |
| Ogg pages of 5 s instead of 1 s (ffmpeg `-page_duration`) | −0.84 % in Ogg Opus, −0.64 % in Ogg Vorbis | a seek to a page lands up to 5 s before its target; left to writers |
| Segment starts aligned on packets | +15 bytes per segment in Ogg Opus, +10 in Ogg Vorbis | costs bytes, saves none |
| Sounds encoded alone, their packets joined under one set of headers | Ogg Opus: the separate files minus their headers (−148 bytes per sound); Ogg Vorbis: the same samples, but heavier than one continuous encoding | in Ogg Opus, 2 starts of 106 differed by more than −42 dBFS unless the decoder restarts at each segment |
| Other containers for the same packets | bytes per packet: Ogg 2.1 to 2.6, MP4 4.1 to 4.6, Matroska and WebM 6.7 to 7.2, CAF 1.0 | only CAF is lighter (−1.1 %), outside the scope of this specification |

## 11. Separate files on disk and in archives

The comparisons above add up file sizes. Stored, separate files take more: on a disk with 4,096-byte clusters, the
4,725 separate Ogg Opus files with tags occupy 41.14 MB for 30.89 MB of content (+33.2 %), while the 36 TT files
as written for draft 0.2 occupied 36.02 MB. In a ZIP archive each separate file adds 30 + 46 bytes of headers and its
name twice (APPNOTE 4.3.7 and 4.3.12), 124 bytes per file here. `opusenc` adds 512 bytes of padding per file by
default, and ffmpeg 8,192 bytes per FLAC file.

## 12. Draft 0.2: the first Ogg TT files (2026-11-11)

- **Files**: 36 in Ogg Vorbis (quality 0, 24 kHz, mono) and the same 36 in Ogg Opus (20 kbit/s), with 300 ms of
  silence between two lines; 33 to 1,575 segments per file; lists of 57 KB to 2.8 MB, about 1.75 KB per segment.
- **Validation**: all 72 files passed `--validate` with no warning. In a first build, 3 segments of 75 failed by
  1 ms: their start fell exactly on a half millisecond (for example 106,730.5 ms), which JavaScript's `Math.round`
  rounds up and the kit rounded to even. About 4 % of the starts fall on a half millisecond at 24 kHz, and half of
  those round differently: section 11.2 now accepts both.
- **Positions**: checked against a full decode by ffmpeg, exact to the frame in Ogg Vorbis, within 1 ms in Ogg Opus
  (by the energy envelope: at 20 kbit/s the SILK mode does not keep the waveform).
- **More than 999 segments**: the player files had 1,575 lines each; from the 1,000th on, 576 segments had `CUE_ID`
  0 and were in the list only (section 11.2).
- **Reader**: the game computes the frames of every packet (Ogg Opus: the TOC byte; Ogg Vorbis: the block sizes,
  with the block flags of the modes read at the end of the setup header, as ffmpeg's Vorbis parser does), set on the
  granule positions of the pages. To play a line it decodes only the packets that cover it, put back in a small Ogg
  stream: in Ogg Opus, 80 ms of pre-roll and a pre-skip of 0; in Ogg Vorbis, two packets before the line and a few
  after, because in Chromium the second packet decoded did not come out exact either, and the stream lost frames at
  its end (section 11.4). The result is identical, to the bit, to the full decode of the file (checked on more than
  200 lines).
- **Size of the comment header, Ogg Opus**: in every file the list ended beyond the first 61,440 octets, which
  RFC 7845 lets programs ignore; in the player files the summary took the first 100 KB (the description named every
  line, twice), so the chapters were beyond it too.

These files brought the rules on chapter times and chapter numbers (section 11.2), the notes on playing one segment
(section 11.4), and the weight study of draft 0.3.

## 13. Limits

- All audio measurements are on speech: CosyVoice 3 voices, Ogg Opus at 20 kbit/s, Ogg Vorbis at quality 0. The
  header constants hold for any content; the silence results and the variation of the encoder are to be measured
  again on music and sound effects, and at other bit rates.
- The WAV figures on original chunks (section 6.2) are estimates.
- The comparisons against re-encoded separate files rest on one encoding of each line; the reference weight does
  not depend on an encoder run.
- The study (sections 4.1, 4.2, 5 to 9) used the voices of 2026-11-12 before two of them were dubbed again and the
  tutorial added; section 4.3 measures the files as shipped.
- No game engine, audio middleware or tag editor has been tested with these files yet.

## 14. Reproducing

- The files are in the repository of Rìcháng, in `public/voices/`.
- `python kit/make_tt_spec_samples.py --validate <file>` prints for each file its result, its reference weight and
  the bytes of audio that belong to no segment, on a line `weight (section 12)`.
- The writer of the game is `scripts/build-voices-tt.mjs` and its reader `src/platform/tt.ts`; both are also
  available under the MIT License.
- The scripts of the study (re-encoding of the separate files, silence tests, WAV model) are not published in this
  repository.
